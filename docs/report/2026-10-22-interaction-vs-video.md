# 任务三决策：每场景视频动画 vs 交互增强

> 结论先行：**不做「每场景视频动画」，把预算全部投到交互增强（P0→P1→P2）**。
> 视频只保留现有的「结局终极画面」（6 秒 Canvas），不铺到 140 个场景。

## 一、两条路的硬指标对比

| 维度 | A. 每场景视频动画（140 条） | B. 交互增强（P0+P1+P2） |
|---|---|---|
| 素材量 | 140 条 4—6 秒视频 | 0 条视频；组件 + 手势 + 场景脚本 |
| 本地生成可行性 | 8 GB 显存、无视频模型权重与工具链（只有 SDXL/SDXL-Lightning、Stable Audio）；即便临时装 Stable Video Diffusion，单条 4s/512p 在 8GB 上约 10—30 分钟，140 条 = **24—70 小时**，且要串联、对齐、重生成失败片段 | 纯代码，无需 GPU |
| 工期 | 光生成就超过截止时间；还要逐条对齐天气/时间/人物一致性 | P0 约 4h、P1 约 6h、P2 约 6h，**可并行**，6—8 小时可合并 |
| 一致性 | 人物、服装、光线逐条漂移，140 条里只要 10 条崩就毁整体质感 | 由同一套设计变量控制，天然一致 |
| 体积/性能 | 140 条 ≈ 300—500 MB（720p H.264），首屏/场景切换要预解码，弱网与离线承诺直接破功；当前 dist 仅 24.59 MB、断网可跑 | 新增 < 100 KB（CSS/JS），不影响断网与首屏 |
| 可修改性 | 改一句文案就要重录对应视频 | 改代码/参数即时生效 |
| 与文本的关系 | 视频是「背景」，玩家仍在读卡片；**不改变「点按钮」的本质** | 直接改变动作本身（拖、按、找、升），正面回应「交互不够强」 |
| 评审观感 | 静态站点里塞 140 段视频，像 PPT 放映；反而掩盖 Canvas 换场与 3D 的实时性 | 评委亲手拖一次「交付」，记忆点来自参与 |
| 风险 | 生成失败/时间不够 → 0 收益；体积失控 → 回归 R1 类部署问题 | 交互可降级（点击/键盘 fallback），失败也只损失该场景的强化，不影响主线 |

| 方案 | 内容 | 工作量 | 覆盖 | 风险 | 优先级 |
|---|---|---|---|---|---|

## 三、为什么视频方案在「交互更强」这个目标上是伪命题

1. **视频是播放，不是交互。** 玩家仍然只能点「继续」，只是背景动了；这恰好是用户抱怨的「卡片按钮」体验，视频加剧了「被动观看」。
2. **视频与 2.5D/3D 的实时性冲突。** 作品已有指针视差、五种 Canvas 换场、可交互 3D 切片；插入视频会把「实时」降级成「录播」。
3. **140 条视频的维护成本会拖垮最后的回归。** 每次改文案/史料卡/结局，都可能要重录；而交互组件可以随代码一起回归测试。
4. **唯一的例外是已有的 6 秒终极画面**：它只在结局出现一次、由 Canvas 实时绘制（不是视频），这正是「短、可控、加分」的形态，保留并加强即可。

## 四、执行顺序（已开工）

1. **并行（今晚）**：音频扩展接线 / P0 结局交付组件 / P2 两个签名组件 / 剧情树 / 全站卡片特效。
2. **合并（音频 agent 改完 App 后）**：CarryTray、SpotlightFind、FlagRaise 接进 App；补音效回执。
3. **P1 过河**：在 P0/P2 合并通过回归后做；若时间不足，砍掉 P1 保 P0+P2（用户可感知收益最大的部分）。
4. **回归**：walk / 9 结局 / lead-audit / 音频 / 卡片特效 / 剧情树自检 → 重出截图与 PDF → 重打包 → 推送 v1.5。

## 五、验收标准（交互增强）

- 尾声：9 个结局全部可拖拽交付 + 点击两次 + 键盘完成；出错可回弹；reduced-motion 可用。
- 第一夜：3 个名字可手电找到、可键盘点亮、找齐才继续；跳过兜底（若接入）。
- 第三夜：旗面可拖到杆顶，风阻真实但可完成，跳过后流程不卡。
- 所有新增交互：390px 无溢出、无 console error、对比度不变、有音效回执（声音开时）。
- 现有测试不受影响：`.choice` 按钮仍存在（拖拽层的无障碍/回退路径），walk/ending/lead-audit 全绿。
